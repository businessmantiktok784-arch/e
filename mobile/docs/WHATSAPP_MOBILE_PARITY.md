# WhatsApp to mobile capability parity

This matrix compares the current webhook experience with the current native app and verified server contracts. “Mobile” describes implemented code, not a live-device or production-backend verification. WhatsApp uses Meta webhook events; the app uses the API origin configured with `EXPO_PUBLIC_API_BASE_URL`. Both converge on the existing backend and database where the route/service does so.

## Evidence and source paths

- WhatsApp routes: `src/routes/webhook.routes.ts`; mounted without a prefix in `src/server.ts`.
- Webhook verification and dispatch: `src/controllers/webhook.controller.ts`, `utils/whatsapp-signature.ts`.
- Media analysis and canonical persistence: `src/services/geoscience-analysis.service.ts`, `src/services/gemini.service.ts`, `src/services/observation.service.ts`.
- Mobile API source of truth: `mobile/services/api.ts`; user session: `mobile/auth/AuthProvider.tsx`.
- Mobile Home/Explore/Map/Community/detail/Profile: `mobile/app/(tabs)/*.tsx`, `mobile/app/observations/[id].tsx`.
- WhatsApp public number configuration is not copied from a populated environment file. Mobile uses optional `EXPO_PUBLIC_WHATSAPP_NUMBER`; no literal phone number is in app source.

## Overall parity assessment

The mobile app and WhatsApp already share canonical observation/community services for the workflows each exposes. Native reads do not create a second observation store. The app now reuses the backend OTP mechanism and secure session token for account-gated commenting. Complete channel parity is not achieved: native photo-to-analysis/new-observation submission, account history, and several community command families need mobile UI/API integration. A dedicated mobile analysis endpoint does not exist in the inspected routes.
